# Внутренний контур практики 1С

## Зачем нужен контур

Внутренний контур практики 1С нужен, чтобы связать внешний рынок труда с реальной ситуацией в компании.

Внешний контур отвечает на вопрос:

> Что происходит на рынке труда ИТ?

Внутренний контур отвечает на вопрос:

> Подтверждается ли это в практике 1С, расходится ли с нашей ситуацией и требует ли решения по людям, деньгам, найму или удержанию?

Контур не должен быть отдельным продуктом. Он встраивается в текущий Labor Market Radar и использует уже существующую логику:

```text
внешний выпуск
-> структурированный внешний snapshot
-> внутренние данные практики 1С
-> сверка рынок <-> практика
-> управленческий вывод
-> локальный рабочий дашборд
```

## Режим размещения

На текущем этапе продукт развивается в одной папке проекта `Обзор РТ`, но с двумя режимами использования.

### Публичный режим

Публичная GitHub Pages-страница остается внешней витриной продукта.

В публичном режиме можно показывать:

- описание продукта;
- внешний рынок;
- публичный внешний snapshot;
- демо-дашборд;
- обезличенные или внешние данные;
- ограничения продукта.

В публичный режим нельзя подгружать реальные внутренние данные компании.

### Локальный рабочий режим

Внутренний контур практики 1С собирается локально внутри текущего проекта.

В локальном режиме можно использовать:

- внутренние показатели практики 1С;
- данные по вакансиям;
- данные по кандидатам;
- данные по офферам;
- причины отказов;
- текучесть и причины;
- показатели планирования численности и загрузки;
- обезличенные выгрузки из общих рабочих чатов, если они согласованы и безопасны.

Локальный рабочий режим не должен публиковать внутренние данные в GitHub.

## Где хранить внутренние данные

Внутренние данные практики 1С хранятся локально в папке:

```text
data/internal_1c/
```

Эта папка должна быть исключена из Git через `.gitignore`.

В нее можно складывать:

- исходные внутренние выгрузки;
- промежуточные очищенные таблицы;
- локальный внутренний snapshot;
- сверки рынка и практики;
- рабочие файлы для анализа практики 1С.

В нее нельзя складывать данные, которые планируется публиковать на GitHub Pages.

Если нужно сохранить пример структуры для разработки, он должен быть синтетическим или полностью обезличенным и лежать отдельно от реальных внутренних данных.

## Реперные точки практики 1С

Первые реперные точки, которые можно начинать использовать в продукте:

| Реперная точка | Что показывает |
|---|---|
| Утилизация | Есть ли перегруз или недозагрузка людей |
| Плановая выручка | Какой объем работы ожидается |
| Фактические поступления | Насколько реальность совпадает с планом |
| Кассовый разрыв | Есть ли давление на решения по численности, найму или расходам |
| Выручка на человека | Эффективность и нагрузка на команду |
| План по численности | Сколько людей нужно держать, нанимать или высвобождать |
| Открытые вакансии | Где есть потребность в людях |
| Количество кандидатов | Есть ли рынок под потребности практики |
| Зарплатные ожидания кандидатов | Насколько ожидания совпадают с рынком и внутренними вилками |
| Вилки офферов | Насколько практика конкурентна |
| Отказы кандидатов | Где и почему теряются кандидаты |
| Отказы нанимающих менеджеров | Где рынок не дает нужное качество |
| Текучесть и причины | Где есть риск удержания |
| Критичные роли и проекты | Где кадровый риск может повлиять на бизнес |

## Статусы сверки

Для каждого внешнего сигнала нужно определить, что происходит внутри практики 1С.

Допустимые статусы:

| Статус | Значение |
|---|---|
| `подтверждается` | Внешний сигнал виден и во внутренней практике |
| `расходится` | Внешний сигнал не совпадает с внутренней ситуацией |
| `недостаточно данных` | Внутренних данных пока не хватает для вывода |
| `ранний внутренний сигнал` | Внутри практики уже видно движение, которое рынок еще не показывает явно |

## Рабочая таблица сверки

Минимальная структура для первой реализации:

| Внешний сигнал | Что видим в практике 1С | Статус | Возможное объяснение | Что проверить | Что делать |
|---|---|---|---|---|---|
| Зарплатный рост в ИТ замедляется | Кандидаты 1С продолжают просить выше вилки | расходится | 1С может быть отдельным дефицитным сегментом | Проверить вилки, офферы и причины отказов | Подготовить решение по вилкам или ожиданиям к ролям |
| Рынок найма стал более выборочным | По 1С мало сильных кандидатов | частично подтверждается | Общий рынок охладился, но сильные 1С-роли остаются дефицитными | Проверить качество воронки и сроки закрытия | Сфокусировать поиск на критичных ролях |
| Компании осторожнее расширяют штат | У практики есть плановая выручка и загрузка | расходится | Практика может идти против общего рынка из-за pipeline проектов | Проверить утилизацию, план выручки и численность | Подготовить сценарий найма или перераспределения |

## Правила интерпретации

1. Нельзя напрямую переносить вывод по всему ИТ-рынку на практику 1С.
2. Практика 1С может жить иначе, потому что это отдельный сегмент с более узким рынком кандидатов.
3. Расхождение с рынком не является ошибкой. Это повод понять причину.
4. Рекомендация должна быть прикладной: что проверить, какое решение подготовить, кому показать.
5. Если внутренних данных недостаточно, вывод должен быть явно помечен как требующий проверки.
6. Если используются чаты или коммуникации, данные должны быть обезличены и не должны включать личные переписки.

## Что запрещено

Нельзя:

- публиковать внутренние данные практики 1С на GitHub Pages;
- коммитить реальные внутренние выгрузки в Git;
- смешивать публичный внешний snapshot и внутренний snapshot без маркировки;
- показывать внутренние показатели компании как публичную часть продукта;
- использовать личные переписки как источник;
- делать вывод о практике 1С только по общему ИТ-рынку без внутренней проверки;
- выдавать экспертный вывод за математически подтвержденную модель.

## Первый MVP внутреннего контура

Первый MVP называется:

> Сверка внешнего рынка с практикой 1С.

Он должен содержать:

1. внешний сигнал рынка;
2. внутренний факт по практике 1С;
3. статус сверки;
4. возможное объяснение;
5. что проверить;
6. что делать.

На первом этапе MVP может быть таблицей или локальным JSON-файлом. Подключение к дашборду делается только после того, как согласована структура внутренних данных и правила безопасности.

## Локальный демо-дашборд

Первый локальный демо-дашборд внутреннего контура лежит в:

```text
prototypes/labor-market-radar-internal/
```

Он читает:

```text
data/current_radar/radar_snapshot.json
data/internal_1c_demo/internal_1c_snapshot.json
```

`data/internal_1c_demo/internal_1c_snapshot.json` содержит только вымышленные данные и нужен, чтобы показать механику будущего внутреннего продукта.

Открывать демо-дашборд нужно через файл в корне проекта:

```text
Открыть внутренний дашборд 1С.cmd
```

Демо-дашборд не является рабочей оценкой практики 1С. Его задача - показать, как внешний рыночный сигнал связывается с внутренним фактом, статусом сверки, объяснением, проверкой и действием.

## Когда переходить к закрытому веб-сервису

Переход к закрытому веб-сервису нужен позже, когда:

- внутренний контур подтвердит полезность;
- появятся регулярные внутренние данные;
- понадобится показывать результат HRBP, HRD или руководителю практики не с экрана пользователя;
- потребуется пароль, роли доступа или история изменений;
- появится готовность размещать продукт на закрытом сервере.

До этого рабочий вариант остается локальным.
